# Thread Pocket

Thread Pocket 用一个**个人工作区**来管理「持续推进的线索（Thread）」。每条 Thread 由六部分组成：**当前描述**（现在到了哪里）、**行动**（待办与固定日程）、**探索方向**（还没成为承诺的想法）、**等待与阻塞**（依赖外部条件）、**笔记**（一份自由书写空间）与**日志**（按时间保留结果与判断）。它解决的是「隔一段时间回来，如何立刻接上」这个问题。

后端是这个工作区唯一的事实来源；下述 MCP 工具是读写它的正常路径。不要猜测数据结构，也不要尝试绕过工具直接操作存储。

## 记录与归类

「记录一下 / 记一下 / 帮我记」表达的是**捕获意图**，不是存储类型。先判断内容属于哪一类：

| 内容 | 归类 |
| --- | --- |
| 明确要做、可以执行的动作 | `task` 待办 |
| 在等真实的外部反馈或条件 | `wait` 等待 |
| 占据确定时间的活动 | `event` 固定日程 |
| 值得继续探索、但还没成为承诺 | `direction` 探索方向 |
| 参考材料、尺寸、链接等可留存信息 | 写入该 Thread 的**笔记** |
| 已经发生的结果、决策、变化、证据 | **日志** |

一条消息里包含多个独立事项时，拆成多条条目，不要合并成一条。不要用笔记或日志代替待办清单；也不要给待办、日程、方向、等待写正文（它们只有标题与属性），需要展开的内容放进笔记。

**不要编造**：没提到的日期不要补，看不清的内容不要猜。缺少关键信息时先问，或者先按最小信息记录。

只说了主题（例如「记录一下装修」）时，用 `resolve_thread` 解析到该主题的**收件箱**：它是每个 Domain 下承担临时收纳职责的 Thread。`resolve_thread(topic, createIfMissing=true)` 会返回确切的 `thread_id`；**不要**从 `list_threads` 的结果里挑第一条，也不要把内容塞进别的 Thread。

明确点名了某条 Thread，或这是上一轮对话的延续时，以它为准。用 `list_threads(query=...)` 查找，再用 `get_thread` 确认；候选仍然含糊时**问用户**，不要猜 id。

示例：
- 「记录一下装修」+ 12 条待办 → 装修 / 收件箱 下的 12 条独立条目。
- 「我要确认瓷砖尺寸」→ 待办；「等商家回复瓷砖尺寸」→ 等待。
- 「记到装修的选材里：买灯带，色温 3000K」→ 待办「买灯带」+ 笔记里的色温参考。
- 「瓷砖已下单」→ 如果存在对应待办就完成它；只有确实有额外信息时才补日志，不要重复自动日志。

## 读取上下文

接续一件事之前，先读它的当前状态：

1. `resolve_thread` 或 `list_threads` 找到目标。
2. `get_thread` 读取当前描述、未结束条目、笔记与最近日志，并**记下返回的 `revision`**。
3. 需要跨线索看今天该做什么时用 `list_overview`；按关键词找东西用 `search`。

`revision` 是这条 Thread 的版本号。每次写入都会让它 +1，因此可以用它判断「我读到的东西有没有被别人改过」。

## 写入

### 当前描述

当前描述是**此刻成立的结论**（一两句话），不是累积的清单，也不是历史。它回答「现在到了哪里」。只有出现新的、已经成立的认识时才改写它；把变化写进日志。

- `update_thread(summary: ...)` 覆盖当前描述；日志里会自动留下修改前后的值。
- 时间流逝本身不代表描述失效；出现与之矛盾的新事实时才需要重写。

### 条目

- 一次提交多条用 `upsert_entries`：传 `thread_id`、`expected_revision` 和 `entries` 数组，整批在同一个事务里完成，要么全部成功要么全部不生效。
- 新条目自己生成一个稳定 id（如 `entry_<短随机串>`）并写进 `id` 字段，便于后续引用；已存在的条目直接复用原 id。
- 更新已有条目时，只传要改的字段；没传的字段保持原值。`kind` 可以随时改变（方向转待办、等待转行动）。
- 结束条目用 `status`：待办/日程用 `done`，等待用 `resolved`，不想做用 `cancelled`，方向可以 `abandoned`。
- 「受阻的行动」是 `blocked=true` 的待办，并写清 `blocker_reason`；它与「等待」不同：前者是自己的动作被卡住，后者是在等外部结果。
- 删除用 `delete_entry`。移动条目到别的 Thread 用 `move_entry`。
- `scheduled`/`plan` 与 `due` 是独立含义：计划日过期变成「待重新安排」，只有截止日过期才是「逾期」。日程需要 `start`。日期用 `YYYY-MM-DD`，日程用带时区的 ISO 时间；不确定时不要填写。

### 日志

日志保留发生过的事情：结果、决策、证据、判断变化。操作类记录（新增、完成、改期）由服务端自动写入，**不要重复**。只有确实值得留下的额外信息才用 `append_log`。

- 已知发生时间时传 `occurred_at`（带时区的 ISO 时间），不知道就省略。
- 用 `actor` 标明是谁记录的。

### 笔记

每条 Thread 只有一份笔记，可以零散、可以很长、也可以一直空着。`write_note` 会**覆盖**整份笔记，所以写之前先读，保留用户原有的随手记录，不要为了「填满分区」而重写它。

## 冲突与失败

- 写入返回 `409 revision_conflict` 时：重新 `get_thread`，对照新的状态决定怎么改，再用新的 `revision` 重试。**不要**不带 revision 盲目重试，也不要重新创建相同条目。
- 写入结果不确定时（超时、报错），先读回来确认 id 与数量，再决定是否重试，避免产生重复条目。
- 工具报错就如实说明失败，不要声称已经同步。

## 鉴权

这个 MCP 用 OAuth 保护。如果调用返回未授权（HTTP 401），按 `WWW-Authenticate` 里的 `resource_metadata` 走客户端的浏览器授权流程；**不要**向用户索要密码或令牌，也不要让用户把令牌贴进对话。授权范围是 `mcp:tools`，对应同一个人的工作区。

## 边界

- 不要猜测 id，也不要用标题近似匹配来代替解析。
- 不要把「等待」当成待办积压清单，也不要因为没有日期就把方向塞进行动列表。
- 不要替用户做判断：建议不等于承诺，尝试不等于结论。
- 不要把工作区内容发送到无关的外部服务。
- 不要声称完成了没有证据支持的变更。

## 快速参考

| 需求 | 工具 |
| --- | --- |
| 找到 / 建立一条线索 | `resolve_thread`, `list_threads`, `get_thread` |
| 读今天的安排 | `list_overview(view="today")` |
| 读未结束的行动 / 收件箱 | `list_overview(view="actions" / "inbox")` |
| 找内容 | `search` |
| 记录一批条目 | `upsert_entries` |
| 完成 / 解除 / 改期 | `upsert_entries`, `update_entry` |
| 改写当前描述 | `update_thread(summary=...)` |
| 记录发生过的结果 | `append_log` |
| 维护自由笔记 | `write_note` |
| 新建线索 | `create_thread` |
